# `queries/tuned/` — the 99 queries, each carrying the settings it needs

One self-contained `.sql` per query. Run any of them directly:

```bash
mariadb -B tpcds < queries/tuned/query59.sql
```

Generated by `queries/build-tuned.py`; edit that, not these files.

## What each file carries

**`sql_mode` — every file.**

```sql
SET SESSION sql_mode = CONCAT(@@sql_mode, ',IGNORE_SPACE,PIPES_AS_CONCAT');
```

`PIPES_AS_CONCAT` is **required for correctness**, not style. TPC-DS uses the
ANSI `||` for string concatenation in **q5, q66, q80 and q84**; without it
MariaDB reads `||` as logical OR, so the concatenated `id` evaluates to `0` or
`1`. For q5 and q80 that collapses the `GROUP BY ... WITH ROLLUP` and the
query returns **7 rows instead of 100** — with no error. It is applied to
every file so running one standalone is always right.

**`split_materialized=off` — six files.**

```sql
SET SESSION optimizer_switch = 'split_materialized=off';
```

| query | measured | why |
|---|---:|---|
| q59 | **−138.1s** | one of its two CTE references was re-materialised 7,665 times |
| q14 | −17.0s | |
| q2 | −9.5s | |
| q5 | −8.9s | |
| q11 | −5.6s | |
| q27 | −3.7s | |

Session-scoped, so each setting affects only its own query.

## Why per query and not globally

| applied | tier 4+5 total |
|---|---:|
| split on everywhere (MariaDB default) | 971.4s |
| split off everywhere | 867.5s |
| **per query, as in these files** | **777.7s** |

Turning it off globally is worth 10.7%, but it **costs** four queries:

| query | measured |
|---|---:|
| q23 | **+54.0s** |
| q4 | +14.6s |
| q78 | +13.9s |
| q57 | +3.2s |

q23 alone gives back more than every winner except q59. Those four files say
so in a comment, so it is clear the default was chosen deliberately rather
than overlooked.

## What is deliberately *not* set

**Four queries inside the noise.** q22 (−1.3s), q46 (−1.6s), q72 (−1.6s) and
q68 (−1.9s) each measured faster with the setting, but this host's
run-to-run variation is ±8%, so a single run cannot tell a 1.6s gain from a
1.6s fluctuation. Choosing the better of two measurements per query is how
you fit to noise. Together they are worth about 6s of the 777.7s.

**Eighty-five queries never measured.** The split comparison covered tier 4
and 5 only — 40 of 99. The other 59 carry no split setting because there is
no measurement, not because one was taken and rejected.

## Provenance and caveat

Measured on **32K pages / SF=4 / 8G pool / sample 160**, under the tuning in
`report/23-server-tuning-sf4.md`, comparing `32k-s0-t1baseline` against
`32k-t6-nosplit`.

All of it ran on **macOS, where `innodb_flush_method=O_DIRECT` is accepted but
has no effect** — InnoDB's reads are served by the OS file cache and a server
restart does not clear it (`pagesize/test-odirect.sh` demonstrates this). The
q59 result is structural and safe: `ANALYZE FORMAT=JSON` shows 7,665
materialisations regardless of how fast each one is. **The smaller deltas are
not** — they should be re-measured on Linux, where `./reproduce.sh full` runs
the matching configuration.

Re-generate after new measurements by editing `DELTA` in
`queries/build-tuned.py` and running it.
