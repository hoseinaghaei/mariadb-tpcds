# Reproducing the benchmark in Docker

One command, Linux container, nothing installed on the host but Docker:

```bash
./reproduce.sh            # quick   SF=1, 32K pages, tuned queries + config (~25 min)
./reproduce.sh smoke      # smallest run, same shape                        (~20 min)
./reproduce.sh full       # SF=4, 32K pages, 8G pool, as report 23          (~3 h)
```

Results land in `./results/`. The repository is mounted **read-only**, so a
run cannot modify it; generated data and the database live in a named Docker
volume (`tpcds-data`), which a second run reuses to skip generation.

## What a run does

1. Builds `dsdgen` from the TPC-DS sources with `OS=LINUX` (and `-std=gnu17`
   plus a few `-Wno-error=` flags — the C89-era toolkit does not compile
   under gcc 15, which defaults to C23 and has removed K&R definitions)
2. Generates scale-factor data
3. Initialises MariaDB at the chosen `innodb_page_size`
4. Creates the schema and loads the data
5. Creates all 188 indexes (`sql/05`, `11`, `14`)
6. `ANALYZE TABLE`
7. Benchmarks the query set chosen by `QUERYSET` under the settings chosen
   by `TUNED`

Then prints the totals, the ratio, and an answer cross-check.

## Options

Any of these can be overridden as `KEY=VALUE` after the profile:

| variable | default (quick) | meaning |
|---|---|---|
| `SCALE` | 1 | dsdgen scale factor |
| `RNGSEED` | 10 | dsdgen random seed — **leave this alone** to match the published answers |
| `PAGE_SIZE` | 32 | 4, 8, 16, 32 or 64 |
| `BUFFER_POOL` | 2G | `innodb_buffer_pool_size` |
| `SAMPLE_PAGES` | 160 | `innodb_stats_persistent_sample_pages` |
| `QUERYSET` | tuned | which SQL to run — see below |
| `TUNED` | tuned | which server settings — `baseline`, `tuned` or `both` |
| `MARIADB_TAG` | 13.0.2 | base image tag — matches the macOS host exactly |

`QUERYSET` and `TUNED` are separate knobs that unfortunately share a word.
**`QUERYSET` chooses the SQL; `TUNED` chooses the server settings.**

| `QUERYSET` | runs | queries |
|---|---|---|
| `tuned` | `queries/tuned/` — the team's optimized query where one exists (33 of 40), the adapted original otherwise | 40 |
| `tier45` | the adapted TPC-DS text, unoptimized | 40 |
| `all` | the adapted TPC-DS text, unoptimized | 99 |

So the default run measures **both** contributions together. To separate
them, hold one fixed:

```bash
./reproduce.sh quick QUERYSET=tier45 TUNED=both   # server tuning alone
./reproduce.sh quick QUERYSET=tuned  TUNED=tuned  # + the query rewrites
```

Files under `queries/tuned/` carry their own `SET SESSION` lines —
`sql_mode` for every query, `split_materialized=off` for six, and three
buffer settings on q14 — so `QUERYSET=tuned` feeds each file **whole** on
stdin, in one session. The other two sets split on `;` and send statements
separately, which would discard every `SET` before its query ran.

`queries/tuned/` is generated by `queries/build-tuned.py` and committed, so a
clone has it. The container mounts `/project` read-only and cannot regenerate
it; if it is missing, the run stops and says so.

### Does the container reproduce the host's answers?

Yes, and it is checked rather than assumed. Comparing the smoke profile's
results against the macOS run at SF=1, query by query, on the hash of the
sorted output:

| run | Docker | macOS | agreement |
|---|---|---|---|
| matched versions | Linux, **13.0.2** | **13.0.2** | **40 / 40** |
| earlier, mismatched | Linux, 11.4.13 | 13.0.2 | **40 / 40** |

The container is pinned to `mariadb:13.0.2`, the host's exact version, so a
run differs in operating system only. Both checks pass, which also says the
answers are stable across a two-major-version gap.

Getting there required `RNGSEED`. Before it was pinned, the same comparison
found **36 of 40 disagreeing** — q4 returning 8 rows against 6, q31 56
against 44. Nothing was broken: `dsdgen` without `-RNGSEED` simply builds a
different database, so the container was reproducing the method and not the
results. Leave `RNGSEED=10` alone unless you want a different dataset.

Response times still differ between the two, and should — different kernels,
different I/O paths, and `innodb_flush_method=O_DIRECT` actually works on
Linux.

```bash
./reproduce.sh quick SCALE=2 PAGE_SIZE=32 BUFFER_POOL=4G
```

## Why Linux matters here

The original measurements were taken on macOS, where **`innodb_flush_method
= O_DIRECT` is accepted but has no effect** — InnoDB's reads go through the
macOS file cache. Measured on the host: the same scan takes 3.6s genuinely
cold, 2.0s after a restart with the OS cache warm, and 1.7s fully cached,
while InnoDB reports ~22–29k physical reads in both cold cases. Restarting
the server empties the buffer pool but not the OS cache, so a "cold" run is
partly warm, and every page is cached twice.

On Linux, direct I/O works, so this container is the more trustworthy venue.
Expect absolute times to differ from the macOS figures in `report/` — at
SF=1 with a 1 GB pool, q51 took 167s here against single-digit seconds on
macOS.

## Indexes: one file to put them all back

`sql/all_indexes.sql` holds **every secondary index** in the schema — 167 of
them across 19 tables, generated from the live database by
`scripts/dump-indexes.py` so it cannot drift from what is actually there.

```bash
mariadb tpcds < sql/all_indexes.sql        # restore all of them
python3 scripts/dump-indexes.py            # regenerate the file
```

That file is what makes experimenting with indexes safe: dropping one stops
being a one-way door.

To find out which ones are earning their keep:

```bash
./scripts/index-usefulness.sh 4            # or 1
```

It zeroes `INDEX_STATISTICS`, runs the 40 tier-4/5 queries once, and writes
`analysis/index-usage-sf<N>.tsv` and `.md` — every index with its size, rows
read, and a used/unused verdict, the total disk held by never-read indexes,
and ready-to-paste statements for switching the idle ones off.

### "Unused" is not a property of an index

It is a property of an index **and** a workload **and** a configuration. This
project measured the same index set at 16K and at 32K pages and got
*different* answers about which members were idle (`report/17`, `report/22`),
and separately made 16K/SF=1 **40% slower** by adding six indexes at once.
Both mistakes are easy to make in opposite directions.

So the report emits `ALTER TABLE t ALTER INDEX i IGNORED` rather than `DROP`.
Ignoring is metadata-only, takes about 0.15s, reverses instantly, and leaves
the index on disk so the decision can be measured and then unmade. Drop when
you need the disk back; ignore when the question is whether it pays.

## Resource notes

- `full` wants 12G+ given to the Docker VM for its 8G pool; otherwise run it
  as `./reproduce.sh full BUFFER_POOL=4G`.
- The `tpcds-data` volume holds the generated data and the database: about
  3 GB at SF=1, about 35 GB at SF=4. Remove it with `docker volume rm
  tpcds-data`.

## Verification built into a run

A reproduction that silently benchmarks an empty database is worse than one
that fails, so the pipeline checks itself:

- `dsdgen` must build and must produce data
- the running server's `innodb_page_size` must match what was asked for
- `store_sales` must hold rows after loading — an earlier bug passed
  `-TERMINATE N` to `dsdgen`, which strips the trailing `|` the loader needs,
  and `LOAD DATA` then inserted nothing without erroring
- a benchmark that finishes implausibly fast is rejected
- every query's output is hashed verbatim **and** row-sorted, so a real answer
  change is distinguished from row-order instability (q65 and q71 have an
  `ORDER BY` that is not a total order)
