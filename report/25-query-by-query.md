## Each query

### 1. q23 — 72.5s at SF=4, 10.0s at SF=1

**Optimized by Claude** — `queries/optimized/q23-sf4/query23_v3_densekeys.sql`

Was the most expensive query in the suite by a factor of three. `ANALYZE FORMAT=JSON` showed its `frequent_ss_items` CTE being split-materialised **55,882 times** in one branch and 28,222 in the other — 99.1s of the 208.1s the query spent under instrumentation.

`split_materialized=off` was the wrong lever and had already measured +54.0s *slower*: materialising that CTE once meant grouping four years of `store_sales` on a 30-character varchar. The fix was to make the CTE cheap instead — drop the `item` join (its `substr(i_item_desc,1,30)` is functionally dependent on the unique `i_item_sk`, so it splits no group), swap `d_date` for `d_date_sk`, and order the GROUP BY to match `idx_ss_date_item_store_cover`.

Verified at SF=4: original 160.7s → 44.7s, **3.60x**, output byte-for-byte identical. The three CTEs were checked individually as well, since q23 returns a NULL and no rows at this scale and the final answer alone proves nothing. See `report/26-the-last-eleven.md`.

### 26. q70 — 4.5s at SF=4, 0.6s at SF=1

**Optimized by Claude** — `queries/optimized/q70-sf4/query70_v1_nosubquery.sql`

Its `s_state in (...)` subquery looks like a top-5 filter and removes nothing: it groups by `s_state` and then partitions by `s_state`, so every partition holds one row, `rank()` is 1 everywhere and `ranking <= 5` admits all of them. Establishing that cost a second full pass over a 12-month window of `store_sales`. Deleting it preserves the answer exactly — this is a quirk of the published TPC-DS text, not a transcription error.

Also aggregates on `ss_store_sk` and joins `store` afterwards, so 2.3M rows are grouped on an integer rather than two varchars.

Verified at SF=4: original 11.6s → 3.6s, **3.22x**, output byte-for-byte identical.

### 27. q97 — 3.6s at SF=4, 0.8s at SF=1

**Optimized by Aysha**, adapted — `queries/optimized/Aysha/q97/query97_BEST_no_temp_tables.sql`

Aysha's insight is the valuable part: the original emulates a FULL OUTER JOIN as `(LEFT JOIN) UNION ALL (RIGHT JOIN ... WHERE a IS NULL)`, reading both sides twice. One LEFT JOIN suffices if the catalog-only count is derived arithmetically — `catalog_only = (rows in csci) - (rows of csci that matched)` — which is exact because both CTEs `GROUP BY (customer_sk, item_sk)`, so each pair occurs at most once per side.

Her file built the two sets as **temporary tables**, which are not acceptable for this project, so they are expressed as CTEs here. Nothing else of hers changed.

> **Defect found and fixed in this pass.** The arithmetic needs `where customer_sk is not null` in that count, and the first version omitted it. `ss_customer_sk` and `cs_bill_customer_sk` are nullable, so both CTEs contain rows grouped under a NULL customer — 2,569 of them in `csci` at SF=4. The original scores those as zero in all three columns (its case expressions all test `is not null`, and an equality join never matches NULL), so a bare `count(*)` added all 2,569 to `catalog_only`: **1,141,754 instead of 1,139,185**. Caught by `gen-25.py` comparing `md5_sorted` against the previous suite run.

Verified at SF=4 after the fix: original 7.3s → 3.8s, **1.92x**, output byte-for-byte identical.

### What to look at next

1. **q77** — the one query with a diagnosed cause and no available fix. Its
   plan reaches `store_sales` through `idx_ss_date_cust`, which carries
   neither `ss_store_sk` nor the profit columns, so every qualifying row
   costs a base-table fetch. A covering index on
   `(ss_sold_date_sk, ss_store_sk, ss_net_profit, ss_ext_sales_price)` would
   make it index-only. It needs DDL, which the read-only analysis policy did
   not permit, and it needs the whole suite re-measured afterwards — adding
   six indexes to this schema once made 16K/SF=1 **40% slower**.
2. **q67** — the slowest query that *is* optimized, and its gain is the
   smallest of the group at 1.3x.
3. **The eight from Nafiz** (q7, q8, q10, q11, q33, q37, q57, q74) were
   verified identical when wired in but never timed individually against the
   original. Their contribution is visible only in the suite total.

## Caveats

- Measured on **macOS, where `innodb_flush_method=O_DIRECT` has no effect**
  (`pagesize/test-odirect.sh`): InnoDB's reads are served by the OS file
  cache and a server restart does not clear it. Both runs are equally
  affected, so the SF=4/SF=1 comparison holds, but absolute times would
  differ on Linux. `./reproduce.sh full` runs the matching configuration in a
  container.
- **One run each, and the whole table moves between runs.** This suite was
  run twice back to back on identical files and settings: **408.7s and
  475.4s**, a 16% spread on the total, with no change to anything measured.
  Individual queries swing further — q5 measured 32.2s and 60.0s in
  consecutive passes, q23's original spanned 160.7–213.0s over four, and q38
  (unchanged in both runs) measured 11.2s and 4.5s. Treat every figure here
  as indicative. The ordering is more reliable than any single row, and the
  per-query speedups quoted in the sections — interleaved A/B, best-of-3 —
  are more reliable than either.
- The per-query speedups quoted in the sections come from dedicated
  interleaved A/B runs, not from this table, so they will not divide out
  against these numbers.
- **q71's output order is not deterministic** (its ORDER BY is not a total
  order), which is why results are hashed both sorted and unsorted.
